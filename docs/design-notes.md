# デザインノート(v0.6、CHANGE-v0.6.md 第3a章)

UIチェックポイントの実装前に書く方針メモ。実装後は、実データのスクショと突き合わせて更新する。

## 前提: 第3a章の要点(再掲・自分用の要約)

- 道具の画面。カード3枚横並び・グラデーション・ガラス風・絵文字・宣伝文句・色つきピル・ダミー数字は禁止。
- 罫線と表が中心。角丸2〜4px、影はオーバーレイのみ。色は意味づけだけに使う(`--v6-primary`/`--v6-fail`/`--v6-pass`/`--v6-review`)。
- 状態は「■ 合格」のような四角い印+文字。色だけに頼らない。
- 画面ごとに構成を変える(一覧は表、詳細は2カラム、実行中はタイムライン)。
- 中身は実データ(`runs/samples/`)で確認する。
- 文言は具体的・事務的・丁寧語。宣伝文句は書かない。
- 日本のQA現場の用語(プロジェクト/テストスイート/テストケース/画面定義/期待結果/実行結果/エビデンス/不具合票/再テスト)を使う。見た目の模倣(T-DASH等)はしない、構造と用語だけ参考にする。

## 既存の土台(v0.6 P1〜P2ですでにある)

- デザイントークン: `web/src/main/resources/static/style.css`の`.v6-*`クラス一式(既に第3a章のトークンに沿って実装済み)。
- 共通ヘッダー: `templates/fragments/shell.html`の`header`フラグメント(製品名・ナビ・ログイン中メールアドレス・ログアウト)。
- 状態表現: `.v6-mark`(`.pass`/`.fail`/`.review`/`.info`、「■ 」+文字)。
- 罫線ベースの表: `.v6-table`。
- 空の状態: `.v6-empty`。

これらは新規画面でも引き続き使う(作り直さない)。

## 画面ごとの構成方針

### 1. ログイン(既存、微調整のみ)
- 中央寄せの狭い1カラム(`.v6-shell.narrow`)。フォーム+エラー表示+リンク。すでに宣伝文句・グラデーションなし。
- 変更点: なし(P1補修で確認済み)。第3a章の観点で見て問題なし。

### 2. オンボーディング(新規)
- ウィザードではなく、**チェックリスト形式の1画面**にする(第3a章「定型のヒーロー」を避けるため、複数画面を跨ぐ派手なステッパーUIにしない)。
- 構成: 罫線区切りの縦積みリスト。各項目は「済み/未」の`.v6-mark`+項目名+短い説明+行動ボタン。
  1. 組織の作成 → 済み(サインアップ時に自動作成、表示のみ)
  2. プロジェクトの作成 → 未なら「作成する」ボタン
  3. ドメインの所有確認 → プロジェクトがあれば「確認する」リンク(プロジェクト詳細へ)
  4. 仕様書のアップロード → 任意(スキップ可の注記)
  5. 最初の診断 → 診断開始へのリンク(所有確認済みのときだけ活性)
- ログイン後、プロジェクトが1件も無いユーザーにだけ表示する(`/`または`/onboarding`。プロジェクトがあれば`/projects`へ)。
- 「やらないこと」との対応: 中央揃えの大見出し+2ボタンのヒーローにしない。チェックリストは罫線区切りの表形式に近い構成にする。

### 3. ダッシュボード(新規)
- 罫線区切りの情報密度が高いレイアウト。カードを均一に3枚並べる典型は避け、**上段に数値の要約(表形式、カードではない)、下段に一覧(表)**という2段構成にする。
- 上段: 「今月の実行回数」「今月のコスト実測(円換算はしない、USDのまま)」「未対応の不具合件数」「直近7日の検出件数の推移」を、**罫線区切りの横並びの数値ブロック**(角丸カードではなく、`.v6-table`の1行に近い見た目)で表示。数値は実測値のみ(`runs/`から集計。ダミー数字は出さない。実行が無ければ「まだ実行がありません」の空状態)。
- 下段: 「最近の実行」を表で(列: 実行日時・プロジェクト・対象URL・状態・指摘件数・コスト)。行クリックで実行詳細へ。
- 「注意が必要な項目」: 予算超過・ドメイン未確認のまま作成されたプロジェクトなどを、`.v6-note`/`.v6-error`のリストで。
- 「やらないこと」との対応: 意味のないグラフ・ダミー数字を出さない。実行が無い組織では素直に空の状態を出す。

### 4. プロジェクト詳細(既存を拡張)
- 現状(P1〜P2)は概要+ドメイン確認+診断開始+空のプレースホルダー(実行履歴・仕様書)。
- タブ構成(第3a章の指示通り)に変更: 概要／実行履歴／仕様書／設定・ドメイン確認。テスト項目・不具合はタブとしては後回し(P3後半以降、データが無ければ作らない)。
- タブは`.v6-nav`と同じ罫線下線スタイルを流用(新しいタブコンポーネントを増やさない)。
- 実行履歴タブ: 表(列: 実行日時・状態・指摘件数・コスト・所要時間)。P3前半でRun/PlanをProjectに紐付けて初めて実データが入る。
- 「やらないこと」との対応: タブの見た目はカードではなく罫線下線(既存`.v6-nav`と統一)。

### 5. 実行詳細(既存`run.html`を洗練)
- 現状もKPIカード・タブ・ドロワーで概ね罫線ベース(v0.5時代の`.card`/`.badge`系クラスとv0.6の`.v6-*`系が混在している)。
- 方針: **実行中はログ形式の縦タイムライン**(第3a章の指示通り)。すでに`renderTrace`に近い実装があるため、見た目をv0.6トークンに寄せる(角丸を`.v6-radius`に、バッジを`.v6-mark`に置き換え)。
- テスト項目書は「Excelの項目書のような表」(列: 項目ID・観点・前提条件・手順・期待結果・結果・エビデンス)。日本のQA現場の慣習に合わせ、既存の`renderCases`のテーブルを見直す。
- 不合格の手順は、期待結果と実際の結果を左右に並べる(差分表示)。既存の`findingCard`のドロワー(`showFindingDrawer`)を、左右2カラムのレイアウトに寄せる。
- v0.5系クラス(`.card`/`.badge`/`.chip`等)からv0.6系(`.v6-*`)への全面移行は、影響範囲が大きいため、**この画面から着手し、他の旧画面(`index.html`/`plan.html`/`history.html`)は次のUIチェックポイントで追う**(段階移行。1回のコミットで壊さない)。

### 6. 不具合一覧(新規)
- プロジェクト横断、または実行横断で指摘(Finding)を一覧表示する画面。表形式(列: 検出日・プロジェクト・観点・重大度・確度・状態・担当者)。
- Q-8(状態・担当者・コメント)は今回のUIチェックポイントでは**表の列だけ用意し、実際の更新機能(状態変更・担当者アサイン)はP6以降で実装**(データが無い機能を先に見せ場だけ作らない)。
- フィルタ: プロジェクト・重大度・状態(セレクトボックス、`.v6-field`のselectを流用)。
- 「やらないこと」との対応: 重大度は色つきピルではなく、`.v6-mark`+文字(High/Med/Low)。

## 空・エラー・読み込み中の状態(全画面共通の方針)

- 空: `.v6-empty`+「次にやること」を必ず書く(例: 「プロジェクトがまだありません。『プロジェクトを作成』から〜」は既に実装済みパターン)。
- エラー: `.v6-error`+原因+次の行動(既存の`error.html`のパターンを踏襲)。
- 読み込み中: 新規`.v6-skeleton`(灰色の矩形、`animation`は使わず静的でよい。第3a章はローディングスピナーを禁止していないが、既存v0.5の`.loading-spinner`は流用可。新規画面では素朴なテキスト「読み込んでいます…」でも可、過剰な演出はしない)。

## キーボード操作

- 表の行: `tabindex="0"`+Enterキーで詳細へ遷移(既存の`th:data-href`+クリックイベント方式に、`keydown`ハンドラを追加する形で対応。P1補修で導入した「JSでonclickを文字列連結しない」方針を維持)。
- ドロワー: 既存の`run.html`の`openDrawer`にEscで閉じる処理が無ければ追加する。
- フォーカスの見た目: `.v6-field input:focus`等ですでに`outline: 2px solid var(--v6-focus)`を設定済み(第3a章のトークン`--v6-focus`と一致)。

## 「AIっぽさチェック」のやり方(実装後に自分で行う)

1. 各画面のスクショを`docs/screenshots/v0.6/`に保存(実データ、デモサイト・デモ組織のみ)。
2. 第3a章の「やらないこと」10項目それぞれについて、スクショを見て該当しないか確認する(チェックリストとして`docs/STATUS-web.md`に結果を記録)。
3. 可能であれば、このサービス自身のUI(ログイン後の画面)を、自分の診断機能(P-UX・P-A11Y観点)にかけてみる(S-6の自己診断の一部。時間があれば)。
