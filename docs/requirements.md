# 要件定義（v0.3.1）— 実装向けの写し

正はNotionの「要件定義: サイト点検エージェント（仮称）」。ここは実装担当が読むための写し（2026-09-20時点）。
差異や不明点は `docs/QUESTIONS.md` に書き、Notionを優先する。優先度・工数・閾値はすべて提案値。

## 1. 概要
- **何を作る**: URLとゴールを渡すと、AIエージェントが自律的にサイトを実際に操作して点検（誤字・不整合・導線の詰まり・法令表示の抜け・簡易セキュリティ）した上で、連打や想定外の操作を実際に試して堅牢性を確かめ（脆弱性診断）、証拠付きレポートを出す。危険な操作は実行前に統制され、承認済みのテスト計画の範囲でだけ実行する。
- **テーマ**: 「業務を自律化するAIエージェント」= Web運用担当の点検業務を、目標だけ渡せば計画・実行・検証・報告まで自走する。
- **打ち出し**: 「言わずに去るユーザーの代わりに、先に使ってみるAI」。ユーザーが問い合わせてくれない小さな不具合・使いにくさ（声なき離脱の原因）を先回りして見つける。
- **差別化の4本柱**: ①統制された自立化（全アクションを実行前に評価。許可ドメイン外は遮断、注文確定は承認待ち）②ペルソナ実操作×観点横断（一貫性×法令表示）③コストが見える自立化（Named Router＋実測）④壊れない自立化（エージェント自身の障害耐性）。
- 「業界初」とは言わない（競合は多い。詳細は Notion）。

## 2. 評価基準（主催 第2回。Day1資料）と、この案の対応
| 評価項目 | この案の対応 |
|---|---|
| ① セキュリティ（情報漏洩・不正操作への対策の設計） | 全アクションのFirewall/ポリシーゲート（許可ドメイン外は遮断、注文確定は承認待ち、`cap_cost`）。Guardrails（PIIマスク、インジェクション検査）。スコープ付きAPIキー。プロンプト・出力は保持されない。監査ログ。L4は承認済みテスト計画内のみ |
| ② コストパフォーマンス（品質とコストの最適化） | Named Router（無料→安価→強いモデルへ段階）。コストを `usage.cost_usd` と `GET /v1/generation` で実測。同一入力で「強いモデル直指定」と比べ、検出率・誤検知を保ったままの削減率を**実測値で**示す |
| ③ 信頼性・堅牢性（想定外の入力・エラーで安定、復旧） | **診断するAI自身**の障害耐性: リトライ（`Retry-After`）、別ベンダーへのフォールバック、無料→有料の切替、劣化運用、中断再開、障害注入デモ、リプレイ。（L4は「診断対象」の堅牢性を確かめる機能で、別物） |
| ④ 自律性（状況を判断し、必要なツールを選ぶ） | ゴールだけで計画→操作→判断→報告まで自走。どのテストを実施するか（テスト計画）を状況から自分で選ぶ。モデル選択はコードに書かず Named Router に任せ、難所だけ強いモデルへ。人は危険操作の承認だけ |
| ⑤ アイデア・独創性（新しさ＋サービス化。事業性も含む） | 「先に使ってみるAI」。任せる範囲＝点検の計画・実行・判断・報告。ペルソナ実操作×連打などの想定外の操作×観点横断。事業性（市場・ニーズ・ビジネスモデル）はピッチで示す（`docs/pitch.md`） |
| OrcaRouter賞（10万円・決勝進出チーム） | 活用度を最重視。**実測して設計に反映**していること（設計判断ログ、コスト比較、Firewall/Guardrails、Fallback）を示す |

| NFR-04 | 可用性: 会場のネットやLLMが不調でも、リプレイで完走できる。事前録画動画も用意 |
| NFR-05 | 安全性: 許可ドメイン外へ通信しない（egress制限）、通常操作はレート制限、破壊的操作は承認制、テストデータのみ使用、APIキーはGit管理外。L4の連打だけは、承認済みテスト計画の範囲（1テストあたり最大10回・100ms間隔）を例外とする |
| NFR-06 | 法務: 診断対象は自作デモと自分たちのサイトのみ。能動的なテスト（L4）は、自作デモ／自分たちのテスト環境に限定。他社サイトや本番への実施は、所有確認・管理者の承諾・テスト環境の指定が前提（不正アクセス禁止法・業務妨害の観点）。法令関連の指摘は「リスクの可能性」の表記に統一し、断定しない（弁護士法72条の観点） |
| NFR-07 | 観測性: 各LLM呼び出しをOrcaRouterのログで確認でき、自前の実行JSONにも記録する |
| NFR-08 | 再現性: デモサイトで、L1〜L3の仕込み8件中6件以上、L4の仕込み6件中4件以上を検出（提案値）。temperatureは低めに固定 |
| NFR-09 | 開発速度: 単一プロセス、DBなし、依存は最小 |
| NFR-10 | 安全なテスト: 非破壊。無害なマーカー文字列のみ使用し、攻撃の連鎖・認証回避・データ持ち出しは行わない。テスト環境フラグのない対象ではL4を無効（初期値OFF） |

## 8. アーキテクチャ方針（決定 2026-09-20、v0.4で更新）
- **2層構成**: ワーカー（ブラウザ操作エージェント。Python）と、Webアプリ層（`web/`。Java／Spring Boot）。**ハッカソンでも両方作る**。Java層は最小構成（ジョブ作成・実行状況・承認・レポート表示）。認証・課金・DBは作らない。
- Java層はLLMを直接呼ばず、ワーカーをHTTP（`docs/contracts.md` のワーカーAPI）で呼ぶ。ワーカーはHTTP APIとCLIを持ち、UIは持たない（承認のフォールバックとして `--approve-cli`）。
- 2つの実装セッションは、データ契約とワーカーAPIだけを境界に並行開発する（担当ディレクトリは `CLAUDE.md` 第5a章）。Java側は、モックワーカーとサンプル `run.json` で先に進める。
- ピッチでは、この2層構成を構成図で示し、画面でジョブ作成→自走→承認→レポートを一気通貫に見せる（評価⑤の「サービス化」の根拠）。
