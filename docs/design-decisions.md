# 設計判断ログ（観察 → 判断 → 固定）

OrcaRouter賞と評価②③④の根拠になる。**「何を測り、何を根拠に、どう決めたか」**を、実測値つきで残す。ピッチで使う。
測っていない数字は書かない。

## 書き方
各判断について、次の形で追記する。

### 判断N: （タイトル。例: Named Routerの候補モデルを3本に絞る）
- 日時:
- 観察（何を測ったか。実測値と、その出所: `bench/results/...`、`GET /v1/generation` など）:
- 判断（何を選び、何を捨てたか。理由）:
- 固定した設定（モデルID、Strategy、Fallback、上限など）:
- 影響（コスト・遅延・検出率・誤検知の変化）:

## 判断の一覧(実測が必要なもの。キーのスコープ拡張後にここへ追記する)
- （判断1）`orcarouter/auto` の観察（遅延・コスト・選ばれたモデル）→ 固定するモデルの決定 — **未実施**(このキーは`orcarouter/auto`へのアクセス自体が`block_key_scope`で拒否される。下記「判断9」参照。コンソールでスコープを広げてもらう必要がある)
- （判断2）候補モデルの絞り込み（2〜4本）とFallback（別ベンダー） — **未実施**(スコープ拡張待ち)
- （判断3）無料モデルの制限への対処（`err_free_*` の扱い、スクショの縮小） — 対処コードは実装済み(判断6)。**実際に`err_free_rate`(429、`retry_after_seconds`=27357秒)に到達し、正しく穏やかに終了することを確認**(判断9)
- （判断4）エスカレーション（難所だけ強いモデル）の条件 — **未実施**(スコープ拡張待ち)
- （判断5）強いモデル直指定との比較結果（検出率・誤検知・コスト・所要時間） — `bench/run_bench.py` は実装済み。無料モデル同士の1回の実行(判断9)はあるが、**強いモデルとの比較はスコープ拡張待ちで未実行**

## 実装が先行した判断(実測不要・設計判断として先に記録)

### 判断6: LLM呼び出しの再試行・フォールバック設計
- 日時: 2026-09-20
- 観察: CLAUDE.md第3章の仕様(429/`Retry-After`、5xx、無料枠拒否4種、Fallback用`extra_body`)を読み、実際に無効キーで`https://api.orcarouter.ai/v1`へリクエストしたところ、401が`{"error":{"code":"","message":"Invalid API key (request id: ...)","type":"orcarouter_api_error"}}`という構造化JSONで返ることを確認(エンドポイントは生きている)。
- 判断: (1) 401/403は再試行しても直らないため即座に諦め、無駄なリトライで時間を消費しない設計にした(他のエラー種別とは異なる扱い)。(2) `err_free_prompt_cap`/`err_free_access_denied`は、同じプロンプトの再試行が無意味なため、環境変数`ORCA_PAID_FALLBACK_MODEL`が設定されていれば即座にそちらへ切り替える(無料→有料の自前切替)。(3) 429で`retry_after_seconds`が無いときは「上流タイムアウト」として通常のバックオフを使う(CLAUDE.md の記載通り)。(4) フォールバックのモデル一覧(`ORCA_FALLBACK_MODELS`)は環境変数から読み、コードにモデルIDを書かない(AC-19)。
- 固定した設定: `LLM_MAX_RETRIES=4`(既定)、`LLM_MAX_RETRY_AFTER_SEC=20`(デモが長時間止まらないための上限。仕様の「Retry-Afterを守る」は尊重しつつ上限を設けた)、`LLM_TIMEOUT_SEC=30`。
- 影響: フォールトインジェクション(429/5xx/timeoutを実際に発生させず擬似的に起こす仕組み)で単体テストした結果、いずれのケースでも例外を外に漏らさず`degraded=True`で復旧できることを確認(FR-30)。実際のOrcaRouterのレート制限・無料枠拒否の挙動は、有効なキーが無いため**未確認**。

### 判断7: ポリシーゲートは自前実装を既定にし、Firewallはベストエフォートで併用
- 日時: 2026-09-20
- 観察: Firewall評価API(`POST /api/v1/firewall/evaluate`)のリクエスト/レスポンス形式がドキュメントで確認できておらず(CLAUDE.md 第15章)、専用キーも未発行。
- 判断: 自前`PolicyGate`(許可ドメイン外deny、L4の回数/間隔上限deny、注文確定等はpending_approval)を常に評価し、それが`deny`のときは絶対条件に関わるためFirewallの判定があっても上書きしない(多層防御)。Firewallキーが設定されていれば追加でベストエフォートに呼び、成功すればその判定を採用する。失敗・未設定なら自前の判定を使い、`PolicyVerdict.source`に`"firewall"`か`"local"`かを必ず記録して隠さない(CLAUDE.md第2章の指示通り)。
- 固定した設定: なし(実行時に`ORCA_FIREWALL_KEY`の有無で自動切替)。
- 影響: 許可外ドメインへの遷移拒否(AC-3)、L4の回数上限超過拒否(AC-13)、注文確定の承認待ち(AC-2)を、擬似LLM応答での結合テストで確認済み。Firewall評価APIとの実接続は**未確認**。

### 判断8: デモサイトの決済処理に擬似遅延(0.25秒)を入れた
- 日時: 2026-09-20
- 観察: `rapid_click`(100ms間隔)をPlaywright経由で試したところ、ローカルサーバーの応答が速すぎて(数ms)、1回目のクリックによる画面遷移が完了してから2回目以降のクリックが発生し、2件目以降が実際には送信されない(=二重注文が再現できない)ことが分かった。curlで直接複数回POSTした場合は再現していたため、「サーバーに二重送信防止が無い」という仕込み自体は正しいが、ブラウザ操作を通した現実的な再現には、実際の決済ゲートウェイ相当の処理時間が必要だと判断した。
- 判断: `/checkout/confirm`の処理に`time.sleep(0.25)`を入れ、1回目のリクエスト処理中に2回目のクリック(100ms後)が届くようにした。これは仕込みの脆弱性(二重送信防止なし)自体を変えるものではなく、ローカルデモの応答速度を現実の決済処理速度に近づけただけ。
- 固定した設定: `demo-site/server.py`の`/checkout/confirm`に`time.sleep(0.25)`。
- 影響: 修正後、`rapid_click(count=5, intervalMs=100)`で実際に5件の注文が作成されることを確認(AC-10)。この過程で、L4マクロツール4種(`rapid_click`/`navigate_direct`/`fill_abnormal`/`tamper_param`)のツールスキーマ(`testId`/`intervalMs`)とPython実装の引数名(`test_id`/`interval_ms`)が不一致という実装バグ、および`BrowserSession.approved_test_ids`を`set(...)`でコピーしてしまいテスト計画承認が反映されないバグも発見・修正した(擬似LLM応答での結合テストで発覚。実LLMなしでも配線のバグは見つけられることを確認)。

### 判断9: 実キー到着後にわかったこと(WP0、2026-09-20)
- 日時: 2026-09-20(`ORCAROUTER_API_KEY`受領当日)
- 観察: `GET /v1/models`は9件のみ返した(`orcarouter/free`・`orcarouter/fusion`系・`orcarouter/auto`と、`deepseek/deepseek-v4-flash-free`等`-free`直接モデル4種)。`orcarouter/free`(1回目)・直接`-free`モデルでの通常呼び出し・ツール呼び出し・構造化出力・Vision(画像入力)は成功。一方、`orcarouter/auto`・`orcarouter/fusion*`・有料直接モデル(`google/gemini-2.5-flash`等)、および2回目以降の`orcarouter/free`呼び出しの一部は `403 model_access_denied`(`reason: block_key_scope`、`manage_url: https://www.orcarouter.ai/console/token?ref=block_key_scope`)で拒否された。`GET /v1/generation?id=`のレスポンスは`{"data":{"total_cost":...}}`という入れ子で、フラットだと誤解していたため`fetch_settled_cost`のバグを1件修正した(`agent/llm.py`)。さらに、実運用で`err_free_rate`(429、`retry_after_seconds: 27357`=約7.6時間)に実際に到達した。
- 判断: (1) このAPIキーは「無料モデルのみ許可」のスコープに制限されていると判断し、当面は直接の`-free`モデルID(例`deepseek/deepseek-v4-flash-free`)を`ORCA_MODEL`に設定して動かす。`orcarouter/auto`・Named Routerを使うには、人にコンソールでスコープを広げてもらう必要がある(`docs/orcarouter-notes.md`に依頼済み)。(2) `retry_after_seconds`が非常に大きい値(時間単位)になり得ることを踏まえ、`LLM_MAX_RETRY_AFTER_SEC`で上限を切って待ちすぎない設計(判断6)を実運用でも維持する。(3) `fetch_settled_cost`のレスポンス解析をネスト構造に合わせて修正。
- 固定した設定: 暫定 `ORCA_MODEL=deepseek/deepseek-v4-flash-free`(直接モデルID。スコープが広がり次第、Named Router名に切り替える。AC-19は維持: この値は環境変数のみで、コードには書いていない)。
- 影響: 実LLM・実ブラウザでの結合テストに合格(`runs/samples/run-8fff06d407/`)。6ステップ、コスト実測$0(無料モデル)。LLM自身が価格不一致(High)・誤字(Low)・返品特約の不明示(Med)を検出し、ルールベースの送料不一致チェック(判断とは別、L1・confirmed)と合わせて計4件の指摘。無料枠のレート制限に到達した後は、エージェントが例外を外に漏らさず`abandoned`として穏やかに終了することも実運用で確認できた(FR-30が実際に機能した)。

### 判断10: Java層(web/)のSpring Bootバージョン選定(評価⑤・サービス化の根拠)
- 日時: 2026-09-20
- 観察: `start.spring.io`(Spring Initializr)に`bootVersion=3.5.6`を指定すると400エラー(`Spring Boot compatibility range is >=4.0.0`)で、3.x系の新規生成を受け付けなくなっていた。Maven Centralには`spring-boot-starter-parent`の3.5.6・4.0.0とも実在を確認済み。
- 判断: エコシステムの現在地(Initializrが4.0以上のみを前提にしている)に合わせ、**Spring Boot 4.0.0**を採用。Java 25(Temurin、環境にインストール済み)で動作することをビルド・起動の両方で確認済み(pom.xmlのターゲットはJava 21)。
- 固定した設定: Spring Boot 4.0.0、Java 21ターゲット。詳細と、実装中に踏んだ問題(JSONエンジンがJackson 3系に既定変更されたことによる`RestClient`自動設定の不整合と、その回避策)は`docs/STATUS-web.md`に記録。
- 影響: 最終的に実ワーカー・実LLMと結合した状態で、ジョブ作成→自律実行→承認→レポート表示まで一気通貫で動作を確認できた。

### 判断11: 有料モデルへのスコープ拡張後、暫定的に google/gemini-3.5-flash を既定に
- 日時: 2026-09-20
- 観察: 人がコンソールでスコープを拡張した後も `orcarouter/auto` は引き続き `block_key_scope` で拒否されたが、`google/gemini-3.5-flash` を直接指定すると成功した(ツール呼び出し・コスト取得とも正常)。無料モデル(`deepseek-v4-flash-free`)との比較実行(1回ずつ、`runs/samples/`参照): 無料=6ステップ・指摘4件・$0、有料(gemini-3.5-flash)=16ステップ・指摘7件・$0.101592。有料モデルの方が、アクセシビリティ(label未関連付け)や導線の分かりにくさなど、より細かい観点まで拾った。
- 判断: `orcarouter/auto`自体のスコープはまだ通っていないため、当面は直接モデルID`google/gemini-3.5-flash`を暫定的な既定にする。Named Router作成後は、これを含む2〜4本の候補で`gated_adaptive`を組む。
- 固定した設定: `ORCA_MODEL=google/gemini-3.5-flash`(`.env`。環境変数のみで扱い、コードには書いていない。AC-19維持)。
- 影響: 1回の実行の比較のみなので、検出率・誤検知の統計的な結論はまだ出せない(`bench/run_bench.py`の複数回実行が必要、次の課題)。この過程で `agent/browser.py` の `get_page_state()` が `reason` キーワード引数を受け付けず、律儀に`reason`を付けてくるモデル(gemini-3.5-flash)で `TypeError` になるバグを発見・修正した(無料モデルは`reason`を省略することが多く、これまで表面化していなかった)。

### 判断12: ツール名・プロンプトの言葉選びが、正当な承認済みテストの実行可否を左右する(v0.5・M3)
- 日時: 2026-09-21
- 観察: P-SEC(価格改ざん)のテスト項目(承認済み・`TEST_MODE=1`)を`google/gemini-3.5-flash`で実行したところ、ツール名`tamper_param`(「改ざん」を含む英語toolスキーマ)を見せた状態では、事前承認・非破壊・テストデータのみである旨をシステムプロンプトで明示しても、モデルが実行を拒否し「一般的なセキュリティ対策の解説」を返す挙動を複数回にわたり再現した。ツール名を`override_param`(中立的な語)に変更した瞬間、同じ状況・同じプロンプトで実行に成功した(実測: 変更前は3回連続で拒否、変更後は同条件で実行・`/__test/state`による確認まで完走)。
- 判断: (1) ツールのAPIスキーマに出す**名前そのもの**が、システムプロンプトの許可・文脈説明より強く安全性判定に影響しうる、という前提でツール設計をする。(2) TestCase生成プロンプトにも「攻撃」「改ざん」「脆弱性」等の語を避け、「境界値・異常値の送信テスト」のような中立語で記述するよう指示を追加した(`agent/planning.py`)。(3) この種の拒否は、システムが「LLMの応答から`finish_test_case`のツール呼び出しが得られない」という形で現れるため、`agent/loop.py`は自己申告(`matchesExpected`)が得られないケースを一律`needs_review`にフォールバックし、クラッシュや誤ったpass/fail判定をしない設計にしている(FR-30、③の実例)。
- 固定した設定: マクロツール名を`override_param`(旧`tamper_param`)に変更(`agent/browser.py`・`agent/policy.py`・`agent/judging.py`・`agent/loop.py`・`agent/planning.py`)。
- 影響: モデル依存の拒否は今後も起こりうる(モデルを変えれば挙動が変わりうる、というのはOrcaRouterでモデルを切り替える設計そのものの価値を裏付ける実例でもある)。**測っていない一般化はしない**: 「override_paramなら常に拒否されない」と断定はできず、モデル・プロンプトの組み合わせ次第で再発しうる前提で、`needs_review`への安全なフォールバックを維持する。

### 判断13: コスト実測の記録漏れを、LLM呼び出しの共通入り口に台帳を組み込んで構造的に解消(FR-28)
- 日時: 2026-09-21
- 観察: `docs/STATUS.md`記載の実測コスト合計(約$1.90)に対し、実際のAPIキー利用上限($5)を使い切ったとの報告があり、差額が説明できなかった。調査の結果、`agent/specs.py`の`build_spec()`と`agent/planning.py`の`generate_test_cases()`が返す`llm_calls`を、呼び出し元(`agent/server.py`の仕様書アップロード処理・プラン生成処理)が受け取ったまま**どこにも保存せず捨てていた**ことが分かった(仕様書抽出・項目書生成のLLM呼び出しコストが一切集計に載っていなかった)。また`costUsdSettled`(`GET /v1/generation`の確定額)を取得・記録する経路自体が存在せず、即時値(`costUsdInline`)のみで実測を語っていた。
- 判断: (1) 記録漏れを個々の呼び出し元の直し忘れに依存させず、LLM呼び出しの共通入り口である`agent/llm.py`の`call_llm()`自体に、成功・失敗を問わず`runs/ledger.jsonl`への追記を組み込んだ(`agent/ledger.py`新設)。呼び出し元が戻り値の`llm_calls`を握りつぶしても、台帳には必ず残る。(2) 確定額は別スレッドで非同期・失敗許容取得し、"settlement"種別の行として追記(既存行は書き換えない。取れなければ`costUsdSettled=null`のまま、即時値との差が見える形で残す)。(3) 併せて、1件(run/plan/spec単位)あたり・1日あたりのコスト上限(`LLM_BUDGET_PER_RUN_USD`=既定$0.5、`LLM_BUDGET_PER_DAY_USD`=既定$2.0)を追加し、超過時は`call_llm()`がAPIを呼ぶ前に諦めて`budget_exceeded`を返す(既存の「LLM呼び出し連続失敗」検知の仕組みがそのまま働き、残り作業を打ち切って部分結果のまま終了する。FR-30と一貫)。
- 固定した設定: `agent/ledger.py`(新設)、`agent/llm.py`の`call_llm()`に`context`引数を追加(呼び出し元は`runId`/`planId`/`specId`を渡す)、`agent/config.py`に`LLM_BUDGET_PER_RUN_USD`/`LLM_BUDGET_PER_DAY_USD`。Worker APIに`GET /api/plans/{id}/cost`・`GET /api/runs/{id}/cost`・`GET /api/cost/summary`を追加し、Java層の実行画面「コスト・モデル」タブに目的別内訳を表示。`python -m agent.cost_report`で台帳を集計表示できる。
- 検証: ライブLLM呼び出しはコスト温存のため擬似応答(fakeなOpenAIクライアント)で行い、予算$0.10・1回$0.04のケースで3回目まで許可・以降`budget_exceeded`になることを確認(スクリプトは本コミットには含めず、確認のみ)。あわせて実際の`google/gemini-3.5-flash`呼び出し(1回、403で即時失敗・課金なし)でも、`purpose=spec-extract`・`specId`付きで台帳に記録されることを確認した(判断14参照)。
- 影響: 過去の実行(このコミット以前)のコストは遡って復元できない(台帳が無かったため)。今後の実測はすべて`runs/ledger.jsonl`が正になる。

### 判断14: 実キーのアクセス範囲が401(無効)→403 block_key_scope(モデルへのアクセス権なし)に変化
- 日時: 2026-09-21
- 観察: 判断11では`google/gemini-3.5-flash`への直接指定で正常に呼び出せていたが、本日(コスト記録漏れの調査で判断13の実装を検証する過程で)同じモデルへの呼び出しが**403 `model_access_denied`(`reason: block_key_scope`)**で拒否されることを確認した(`docs/QUESTIONS.md` #19)。以前観測していた症状(401 Invalid API key、`docs/QUESTIONS.md` #17)とはエラーの種類が異なる。
- 仮説(未確認。人による確認待ち): 利用上限($5)到達をきっかけに、コンソール側がキーのモデルアクセス範囲を自動的に制限した可能性がある。断定はできない。
- 判断: この呼び出しは401/403を再試行しない設計(`agent/llm.py`)のため課金は発生していない。原因の切り分けは人のコンソール確認が必要なため、それまではライブLLM呼び出しを伴う検証(ベンチマーク比較・PDF抽出のライブ確認等)を保留し、コード面(台帳・予算上限・bench比較スクリプトの構成共通化)を先に仕上げる。

### 判断15(仮説・未検証): gated_adaptiveがHardプールに偏り、コスト削減にならない可能性
