## はじめに
自分のサービスで、「使いにくい」と問い合わせをくれたユーザーは、何人いるでしょうか。
逆に、使いにくいと感じて、黙って離れたユーザーは、何人いるでしょうか。

僕たちは後者を減らすために、**ユーザーの代わりに、先にサイトを使ってみるAIエージェント**を作りました。
URLとゴールを渡すと、実際にブラウザを操作して、不具合や使いにくさを、証拠付きで報告します。

この記事では、作ったものと、**AIに任せた範囲・任せなかった範囲**、そして実際に測ったコストを書きます。

## 1. 課題：小さな不具合は、報告されない
重大なバグやデザインのミスは、問い合わせで指摘してもらえます。
でも、小さなバグや使いにくさは、わざわざ報告されません。ユーザーは黙って離れます。

### 1.1 本当にそうなのか
- 【要入力】チーム内・身近な人への聞き取り（例: 「使いにくくて、黙ってやめたことがある人」は何人中何人か）。
- 【要入力】その具体例（どのサイトの、どこで、なぜやめたか。実名のサービスは載せず、状況だけ書く）。
- 数字が集まらなければ、この節は「体験談」として書く。調査と書かない。

### 1.2 既存の点検ツールでは足りない理由
- Siteimprove、Silktide、SPIRAL ISSO など、従来の点検ツールは、ルールベースでページ単位が中心。
- 「送料が、特商法のページと決済画面で違う」といった**ページをまたぐ不整合**や、**実際に操作したときの挙動**は、ルールでは拾いにくい。
- 「業界初」とは言いません。AIによるUX診断やエージェント型QAなど、重なる領域はあります。

## 2. 作ったもの：サイト点検エージェント（仮称）
使い方は、次の6ステップです。
1. URLとゴール（例:「購入手前まで進める」）とペルソナ（例:「ITに弱い60代」）を入力する。
2. エージェントが自律的にサイトを操作する。
3. 注文の確定など、危険な操作の前で止まり、人が承認する。
4. 連打や手順スキップなどの**堅牢性テスト**は、エージェントが作った**テスト計画を人が一括承認**してから実行する。
5. 指摘が、スクショ・再現手順・リクエストログ・修正案つきで並ぶ。
6. コスト（1診断あたり／観点別／モデル別）が表示される。

（スクショ: 6ステップの画面。デモサイトのもの。Java層の画面を使う）

### 見るもの
| 観点 | 内容 |
|---|---|
| L1 テキスト・整合性 | 誤字、表記ゆれ、価格や送料の不一致 |
| L2 UI・導線 | ペルソナの目線で、迷う・詰まる箇所 |
| L3 ルール | 特商法の必須項目、同意チェックなど |
| L4 堅牢性テスト | 連打、手順スキップ、価格改ざん、異常入力、エスケープ、エラー露出 |

## 3. 「AIはここだけ」：役割を分けた
全部をAIに任せると、遅く、高く、そして信用できません。だから、役割を分けました。

| 層 | 担当 | AIを使うか |
|---|---|---|
| ブラウザ操作・要素の取得・連打の実行 | Playwright（コード） | 使わない |
| 許可ドメインの遮断・回数と間隔の上限・承認の要否 | ポリシーゲート（コード） | 使わない |
| 次に何を試すか・画面を読んで違和感を見つける・テスト計画を作る | LLM | **使う** |
| 不具合かどうかの最終判定（二重注文が起きたか、など） | リクエストログと、テスト環境の状態確認（コード） | 使わない |

```text:architecture.txt
[Java層 (Spring Boot)] --HTTP--> [ワーカー (Python + Playwright)] --OpenAI互換--> [OrcaRouter] --> 各モデル
  ジョブ作成・承認UI               ブラウザ操作・ポリシーゲート                    ルーティング・コスト記録
  レポート表示                     LLMを呼ぶのはここだけ
```

:::note info
LLMを呼ぶのは、ワーカーだけです。Java層はAPIキーを持たず、ワーカーのHTTP APIだけを呼びます。
:::

1件の指摘は、次のようなJSONで表します（データ契約の抜粋）。

```json:finding.json
{
  "id": "f-001",
  "lens": "L4",
  "testId": "T-01",
  "severity": "High",
  "confidence": "confirmed",
  "title": "注文確定の連打で、注文が複数件になる",
  "evidence": [{ "type": "request_log", "ref": "runs/<runId>/step-12.json" }],
  "repro": ["/checkout を開く", "注文確定ボタンを100ms間隔で複数回押す"],
  "silentChurnRisk": true
}
```

- 画面は、画像ではなく、**テキスト＋操作可能な要素の一覧**でLLMに渡す。画像非対応の無料モデルでも動き、コストにも効く。
- Java層（Spring Boot）は、LLMを直接呼ばず、APIキーも持たない。ワーカー（Python）のHTTP APIだけを呼ぶ。
- 2つのClaude Codeセッションで並行開発し、境界は、データ契約（`docs/contracts.md`）だけにした。

## 4. LLMに、判定までさせるとどうなるか
LLMに「不具合か？」まで判断させると、間違えます。【要入力】実際に起きた誤りを、3点、具体例で書く。例の候補（実際に起きたものだけ書く）:
- 対照として置いた、二重送信対策済みのフォームを、不具合と判定した。
- 二重注文が起きていないのに、「起きたはず」と報告した。
- 表記ゆれではない言い換えを、誤字と判定した。

### 対策
- 二重注文などの**判定は、リクエスト数とテスト環境の状態で行い、LLMの感想では決めない**。
- 状態が確認できない対象では、確度を `needs_review` に下げる。
- 各指摘を、別ステップで再確認する。【要入力】実装したなら書く。していなければ削る。

## 5. 安全：AIを信じない設計
AIに、ブラウザで実際に連打させる。だから、次の3つの備えを、コードで実装した。
1. **範囲**: 診断対象は、許可ドメインとテスト環境のみ。許可外への遷移は、実行前に遮断する。
2. **承認**: 危険な操作は、実行前に人が承認する。連打などは、テスト計画の一括承認が要る。回数は最大10回、間隔は100ms以上。
3. **統制**: すべてのアクションを、実行前にポリシーゲートへ通す。【要入力】OrcaRouter Firewall か、自前のPolicyGateか。使った方を、正直に書く。

個人情報は、LLMに送る前にマスクする。【要入力】マスク前後の例（テストデータ）。
隠し指示を仕込んだページでも、承認なしの危険操作が実行されないことを確認した。【要入力】実測

## 6. 信頼性：このエージェント自身の堅牢性
- LLM側の失敗（429、5xx、タイムアウト、不正なJSON、無料枠の拒否）は、リトライ、別ベンダーへのフォールバック、有料モデルへの切り替えで復旧する。
- 障害を意図的に起こして、復旧を確かめた。【要入力】起こした障害の種類と、復旧した回数
- 通信が不調でも、保存済みの実行結果を再生する**リプレイモード**でデモできる。

## 7. コスト：OrcaRouterで、測って決めた
LLM呼び出しは、すべてOrcaRouter経由。アプリが知っているのは、Named Routerの名前だけ。

### 7.1 観察 → 判断 → 固定
1. `orcarouter/auto` で動かして、遅延・コスト・選ばれたモデルを観察した。【要入力】
2. 結果から、候補を絞って、Named Routerを作った。【要入力】
3. 別ベンダーのFallbackを置いて、切り替わることを確認した。【要入力】

### 7.2 強いモデルの直指定と比べた
同じデモサイト・同じ仕込みで、構成だけを変えた。

| 構成 | 検出率 | 誤検知 | 1診断のコスト | 所要時間 |
|---|---|---|---|---|
| 強いモデルの直指定 | 【要入力】 | 【要入力】 | 【要入力】 | 【要入力】 |
| Named Router | 【要入力】 | 【要入力】 | 【要入力】 | 【要入力】 |

- コストは、`GET /v1/generation` の確定額で集計した。
- 下がらなかった場合も、その結果をそのまま書く。

## 8. 価格を考える
【要入力】1診断あたりの原価（7.2の実測）を根拠にする。実測が無いうちは、この節は書かない。
- 競合の価格は、各社の公式ページで確認できたものだけを表にする。
- 支払意思は、まだ検証していない。数字は出さない。

## 9. できないこと
- ログインが必要なページ、CAPTCHA、決済の実行は扱わない。
- 診断できるのは、許可ドメインとテスト環境だけ。

:::note warn
他人のサイトに無断で使うと、不正アクセス禁止法や、業務妨害の問題になりえます。所有者の同意が前提です。これは法的助言ではなく、リスクの可能性の指摘です。
:::

- 見つけられるのは、仕込んだ不具合の範囲。【要入力】検出率の実測と、見逃したもの。
- 認証・課金・DBは、今回は作っていない。

## おわりに
ユーザーは、不満を教えてくれない。だから、**教えてもらうのを待つのをやめて、先に使ってみる**ことにしました。
そして、AIを信じるのではなく、範囲・承認・証拠で、AIが安全に動ける形にしました。
