# 計測計画（Qiita記事用の実測値。**23:30 以降に実施**）

目的: 評価5項目（①セキュリティ ②コスパ ③信頼性・堅牢性 ④自律性 ⑤アイデア・独創性）と OrcaRouter賞を、**実測値**で示す。測っていない数字は、記事に書かない。
実施者: ワーカー（ライブ計測の実行。OrcaRouter の利用上限が、23:30 ごろ回復）＋指揮官（企画セッション。図の生成、記事の更新）。
予算: 追加で約 $4 まで（日次上限 $13 の範囲。実行前後に `python -m agent.cost_report` の実効コスト合計を記録）。**上限の 80% に達したら止めて、おのゆーへ連絡。**
前提: 機能の実装が一区切り（または凍結）していること。デモサイト（`TEST_MODE=1`、8765／demo-site2 は 8766）とワーカーが起動済み。`ORCAROUTER_API_KEY` が有効。

## 実施の順序（23:30 以降）
1. 指揮官 → ワーカー: 開始の連絡。ワーカーは、起動確認と、実効コスト合計（前）を記録。
2. ワーカー: M5（コスト0円のもの）→ M3 → M4b/c → M4a → M2 → M1、の順に実行（安いものから）。**各計測の後に、実効コスト合計を報告。**
3. 指揮官: 出力（JSON）を受け取り、`build_charts.py` で図を生成し、`docs/qiita-article.md` を更新。数字は、JSONと台帳から、機械的に転記する（手で書き写さない）。
4. 指揮官: 記事の数字を、元のJSONと、1つずつ突き合わせて確認（差し戻しの基準: 記録と一致しない数字は載せない）。
5. 上限に達した、または、ワーカーが止まった場合: そこまでの実測で、記事を完成させ、未測定の項目は「未測定」と書く。

## 注意
- **bench の出力 JSON には、`"sessionAffinity": "OFF"` を必ず書く**（`build_charts.py` が、この印のある比較だけを使う。セッション固定オンの実行や、入力の圧縮などの別条件の実行は、混ぜない）。M2 の実行時は、コンソールの設定がオフであることを、おのゆーに確認する。
- 自動採点（`score_findings`）は、キーワードによる、ベストエフォートの突き合わせ。記事には、「自動採点による概算」と書く。
- 実行は、1回ごとに、ばらつく。**平均と、ばらつき（最小〜最大）**を出す。1回だけの数字は、そう書く。
- 対象は、自作のデモサイトだけ（許可ドメイン）。他社サイトは、対象にしない。
