MiruQA における、入力データの保護・対象サイトの保護・エージェントの制御

MiruQA 開発チーム ／ 2026-09-22 版 ／ 対象コード: 開発ブランチ（Java 110件・Python 152件の自動テストが成功した時点）

要旨 仕様書を読み、実際のブラウザで画面を操作するAIエージェント（MiruQA）は、一般のWebアプリと異なる2種類のリスクを持つ。第一に、利用者が渡したデータ（仕様書、点検対象の画面の内容）が、外部のAIサービスへ渡ること。第二に、エージェント自身が他者のシステムを操作できること（連打・改ざんなどの能動的なテスト、第三者サイトへの意図しない接触）。本稿は、これらの脅威を整理し、多層の防御（認証・データ分離・対象の認可・操作の制限・データ保護・監査）の設計を示し、自動テストと独立したレビューで確認できたことと、確認できていないことを区別して報告する。「安全である」と主張せず、問題になり得る操作を、仕組みとして封じることを目標とした。残る限界（正規表現によるマスクの不完全さ、上流のAI事業者のデータ保持が未確認、法務の確認が未実施など）は、第8章にまとめた。

1. はじめに

MiruQAは、仕様書（txt・md・docx・PDF）から、テスト項目書を生成し、実際のブラウザで画面を操作して、証拠つきの不具合票を作る。この動作は、利用者にとって有用である一方、次の性質のために、セキュリティ上の設計が製品の価値そのものとなる。

  • 外部のAIにデータが渡る。仕様書と画面の内容は、ゲートウェイ（OrcaRouter）を経由して、上流のAIモデルに送られる。
  • エージェントが操作を行う。ボタンを押し、入力し、時には連打する。誤って、または悪用されて、他者のサイトに被害を与え得る。
  • 点検対象の内容を信頼できない。対象のページに、AIへの命令が隠されている場合がある（間接プロンプトインジェクション）。

本稿の貢献は、(1) 脅威の整理、(2) 各脅威に対応する制御の設計、(3) 実装に対する検証の結果と、見つかった不備の記録、(4) 未解決の限界の明記、である。

3. システム構成とデータの流れ

Web層（Java、Spring Boot）が、認証・組織ごとの分離・対象の認可を担当する。ワーカー（Python）が、ブラウザの操作とAIの呼び出しを担当する。Web層は、AIを直接呼ばず、APIキーを持たない。両者は、共有の秘密（HMACの定数時間比較）で認証する。ワーカーは、共有の秘密が設定されていない場合に起動を拒否する（フェイルクローズド）。明示的に無効化した場合のみ、警告つきで無認証を許す。

4. 防御の設計（多層防御）

単一の対策に依存せず、独立した複数の層で、同じ脅威に備える。図2に層構造を示す。上の層が破られても、下の層が、被害の拡大を止める。

4.1 認証とセッション（L1）

  • パスワードはBCryptでハッシュ化して保存する。8文字以上を要求する。
  • ログインを5回連続で失敗すると、15分間ロックし、監査ログに記録する。
  • メール確認のトークンは24時間、パスワード再設定のトークンは30分の有効期限を持ち、1回だけ使える。メール送信は模擬（ファイル出力）で、実際のメールは送らない。
  • すべての変更系のリクエストに、CSRFトークンを要求する。
  • 同時セッションの数に上限（5）を設ける。

4.2 データの分離（L2）

プロジェクト・仕様書・プラン・実行・使用量・監査の全データに、組織IDを持たせ、他組織のデータは、URLを直接指定しても、取得できない。仕様書の取得APIで、他組織のIDを指定すると取得できる不備を、レビューで発見し、修正した（第7章）。修正後は、分離の自動テストが常に実行される。

4.3 ワーカーAPIの保護

ワーカーは、Web層からの要求だけを受け付ける。共有の秘密を、定数時間比較で照合し、一致しない要求は、401で拒否する。秘密が未設定なら、起動しない。

4.4 AIの呼び出しの制御（L6の一部）

  • 非ストリーミングで、自前の再試行と回復を行う（429は待機時間を守る）。
  • 呼び出しの前に、予算（1実行、1日、組織の日次・月次）を確認し、超過なら、APIを呼ばずに終了する。
  • 台帳に、トークン数・費用・モデル名を記録する。プロンプトの本文は、記録しない。

5. 対象サイトの保護：3つのモード

「AIが実際に操作できる」ことは、悪用されれば、第三者への攻撃にもなる。そこで、点検の対象を、プロジェクトの種類で分け、種類ごとに、許可する操作を、サーバー側で決める。種類は、作成後に変更できない（読み取り専用のプロジェクトから、能動的なテストへ切り替える抜け道をなくすため）。

5.1 所有確認とSSRF対策

モードBでは、対象サイトの/.well-known/配下に、発行したトークンと同じ内容のファイルを置く方式で、所有を確認する。確認のためのHTTP取得に先立ち、名前解決した先のIPアドレスを検査し、ループバック・プライベート・リンクローカル・クラウドのメタデータ（169.254.169.254）であれば、取得自体を行わない（SSRF対策）。リダイレクトは追わない。拒否リスト（政府機関の.go.jp・.lg.jp、主催・協賛企業のホスト名）は、いずれのモードでも、登録自体を拒否する。設定の値は、変更できる。

5.2 能動テストの許可（3条件）

連打・改ざん・異常入力といった、状態を変え得る操作は、次の3条件がすべて成立したときだけ実行される（図3）。AIが「承認済み」と自己申告することはできない。

  • 入力に使う文字列は、実行されない無害なマーカーに限る（例: <b>MARKER_XSS_TEST</b>）。スクリプトやSQL文の攻撃的な断片は使わない。
  • いつでも実行を止められる（緊急停止）。停止の応答は、テストで確認している。

6. 入力データの保護

6.1 マスク

AIに送る前に、メールアドレス・電話番号・氏名・住所らしい文字列を、正規表現で、[EMAIL]などに置換する。適用箇所は、仕様書の本文、各ステップの画面テキスト、下見の結果、利用者が追加した文章、の4か所である。この方式は、完全ではない（第8章）。

6.2 画像を送らない

画面の観察は、テキストと操作可能な要素の一覧で行い、スクリーンショットは、AIに送らない。これは、コストと、画像内の個人情報の流出、の両面の対策である。将来、画像入力を使う場合は、マスクの方法を先に決める。

6.3 ゲートウェイのガードレール（OrcaRouter）

アプリ側のマスクに加えて、ゲートウェイ側に、入力の検査ルールを設定した（2026-09-22 時点）。下表は、作成済みのルールである。

表6　作成したガードレールと、状態（管理画面の確認時点）
ルール目的状態

PII シールド個人情報のマスク作成済み・キー未紐付け・原文ログON
シークレット & API キーブロッカーキー・トークンの遮断作成済み・キー未紐付け・原文ログON

更新（2026-09-22）：ゲートウェイの仕様上、1つのAPIキーに紐付けられるガードレールは1つだけで、1つのガードレールに複数のルールを入れる。そこで、上表のルールを統合した合成ガードレールを作り、アプリ用のキーに紐付けた（利用者による設定）。紐付け後に、ダミーの個人情報を使って動作を確認した結果は、次のとおり。
  • メールアドレスは、マスクされた。電話番号（日本の形式）は、ゲートウェイ側では、マスクされずに通過した。アプリ側のマスク（agent/masking.py）は電話番号に対応しているため、二重防御としては機能するが、ゲートウェイ側には、その後、日本の電話番号のカスタム正規表現を追加した（利用者の設定）。再確認（ダミー番号5種）では、ハイフン付き3種はマスクされたが、ハイフンなし11桁（09012345678）と国際表記（+81 90 1234 5678）は、通過した（対照の注文番号・価格・住所は誤マスクなし）。
  • キー風の文字列は、ブロックではなく、[REDACTED] への置換（マスク）になった（設定どおり）。
  • URL（http://127.0.0.1:8765/...）は、改変されずに通過した（IPアドレスのマスクが、影響していないことの確認）。
表6は、統合前の個別ルールの記録であり、統合後の状態は、上記の結果のとおり。

6.4 秘密情報の管理

  • APIキーと共有の秘密は、環境変数で渡す。.envは、バージョン管理の対象外にしている。
  • 実行結果（runs/）と、模擬メールの出力は、バージョン管理の対象外にしている。
  • 点検対象のテスト用アカウント（ログインが必要な画面の点検に使う）は、AES-256-GCM で暗号化して保管する。鍵は環境変数で渡し、未設定なら、保存も復号も失敗する（フェイルクローズド）。実行時にだけ復号し、ワーカーの計画・実行記録・台帳には、平文のパスワードを残さない（記録の検索で、残っていないことを確認済み）。

8. 限界と残るリスク

表10　確認できていないこと・限界
#内容影響

L6セキュリティヘッダー、ログインのレート制限（IP単位）、依存関係の脆弱性スキャンは、未確認・未実施未評価
L7第三者による脆弱性診断（ペネトレーションテスト）は、未実施自己評価に留まる
L8プロンプトインジェクションの耐性は、限られたケースでの確認網羅的ではない
L9利用規約・プライバシーポリシーは、下書きで、法務の確認が未実施商用の前に、専門家の確認が必要

9. 法的な観点

本稿は、法的助言ではない。日本の法令に照らして、他者のサイトへの自動的な操作は、次の点でリスクを持ち得る。

  • 負荷や、実際の注文・送信によって、業務を妨げた場合、偽計業務妨害や電子計算機損壊等業務妨害（刑法233条・234条の2）に問われる可能性がある。
  • 認証や、アクセス制御を回避した場合は、不正アクセス禁止法の問題になり得る。ログイン不要の公開ページの閲覧そのものは、通常、この対象ではない。
  • 自動アクセスを禁じる利用規約への違反は、民事上の問題になり得る。

MiruQAは、これらに対して、問題になり得る操作を、仕組みとして封じることでリスクを下げる（対象の種類の分離、所有確認、宣言と承認、回数・間隔の上限、読み取り専用の強制、robots.txtの尊重、回避しない設計）。ただし、「合法であることの保証」は、ソフトウェアだけではできない。利用規約に、責任の所在（対象の管理者の許可を得ること）を明記し、商用化の前に、専門家の確認を受ける。

10. 今後の課題

  1. ゲートウェイの電話番号の正規表現の追加（ハイフンなし11桁・+81表記）は、今回は見送り。既知の限界として残す（アプリ側のマスクが先に働く）。
  2. 保存時の暗号化（DB、実行結果）。クラウド運用時のHTTPS、セキュリティヘッダー。
  3. 依存関係の脆弱性スキャンと、第三者による脆弱性診断。
  4. プロンプトインジェクションの評価セットの拡充。
  5. 法務の確認（規約、公開ページの点検の扱い）。
