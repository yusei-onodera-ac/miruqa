# ピッチの軸とデモ台本（実装側は、デモで見せる指標・流れの確認用に読む）

ピッチの台本・スライドは別セッション（企画）が担当。実装側は、**デモで見せるもの**が動くように作る。

## ピッチの軸
- 構成: 評価5項目（①セキュリティ ②コスパ ③信頼性・堅牢性 ④自律性 ⑤独創性）に対応して、それぞれ「設計」と「実測」を1つずつ示す。OrcaRouterの活用は、設計判断ログ（観察→判断→固定）とコストの実測（削減率）で示す。
- 課題の構図: 重大なバグやデザインのミスは、ユーザーが問い合わせで教えてくれる。小さなバグや使いにくさは報告されず、ユーザーは黙って離れていく（声なき離脱）。運用側は離脱の理由を知る手段がない。
- 位置づけ: 「言わずに去るユーザーの代わりに、先に使ってみるAI」。ペルソナになりきって実際に操作し、連打や想定外の操作も試して、ユーザーが報告してくれない問題に先に気づく。
- 事業性（⑤の一部。運営が「実際に売れるか、市場があるかもアイデアとして評価。新しさとサービス化のバランスで評価」と回答）: 顧客は中小〜中堅のWeb運用兼務担当者と制作会社。提供形態はSaaS（診断ごとのクレジット制。1診断あたりのコストを実測できることが単価設計の根拠）。まず制作会社向けのクローズドβ。サービス化の壁（他社サイトへの能動テストは管理者の承諾が必要）は、所有確認・許可ドメイン・テスト環境指定で解く。市場規模・支払意思・離脱率の改善効果は未検証で、数字は根拠が確認できるものだけ使う。
- 注意: このプロダクトが示せるのは「小さな問題を先に見つけること」まで。離脱率の改善は実証していない。**実測していない数字（削減率など）は出さない。**

## デモ台本（2分・案）と、実装が満たすべきこと
1. 課題（10秒）。
2. URLとゴール入力、ペルソナ選択（10秒）。→ 入力UI（またはCLI）と、許可ドメインの確認。
3. エージェントが自走（35秒）: 計画→操作→つまずき→再計画。画面と進行ログ、マウスの動き。途中でモデル障害を注入し、別ベンダーへ自動で切り替わって完走する（③）。→ 障害注入モード、フォールバック、進行ログ。
4. テスト計画を提示し、人が承認（15秒）: 「連打」「手順スキップ」「価格改ざん」などの一覧。人の介入は承認1回のみ。→ テスト計画と一括承認UI。
5. 実際に連打して二重注文を再現（20秒）: 画面で連打すると注文が2件になる。承認外の操作や許可外ドメインは遮断される。→ `rapid_click`、`/__test/state`、Firewall/ポリシーゲート。
6. レポート（25秒）: 二重注文（High）、横断指摘（送料の不一致）、誤字・表記ゆれ、コストの実測（強いモデル直指定との比較）とモデル別ログ（②）。→ レポート（コスト・モデル別・回復の指標）、ベンチ結果。
7. 締め（5秒）: 「言わずに去るユーザーの代わりに、先に使ってみるAI」。まず制作会社向けのSaaSから。

会場のネットやLLMが不調でもデモが成立するよう、**リプレイモード**と事前録画を必ず用意する。
