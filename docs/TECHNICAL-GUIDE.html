1. 全体構成

MiruQAは、4つの実行単位から成る。①Web層（Java）、②ワーカー（Python）、③点検対象の例となるデモサイト、④紹介ページ（LP。Java、別の配備）。Web層は、AIを直接呼ばず、APIキーを持たない。AIの呼び出しと、ブラウザの操作は、すべてワーカーが行う。

1.1 設計の原則

  1. AIの呼び出しは、1か所（agent/llm.py）を通る。予算の確認、台帳への記録、再試行、フォールバックを、ここに集約した。
  2. 判定の根拠は、コードで確かめられるもの（リクエスト数、状態確認、画面の差分）を優先する。AIの感想だけでは、「確定」にしない。
  3. 危険な操作は、実行の前に、ポリシーゲートを通す（許可ドメイン、回数・間隔の上限、承認の有無）。
  4. 認可の決定は、Web層が行い、ワーカーへは、決定の結果（モード）だけを渡す。利用者の入力やAIの出力では、変えられない。
  5. モデルのIDを、コードに固定しない。環境変数（ORCA_MODEL）で指定する。

4. サービスロジック

4.1 点検の全体のパイプライン

4.2 仕様書の取り込み（specs.py）

  1. 形式ごとに、コード側で節に分割する（PDFはページ単位、docxは段落スタイル、mdは見出し、txtは番号見出し）。
  2. 各節を、マスクしてから、AI（purpose=spec-extract）で SpecItem（id・本文・節・ページ・種類）に分解する。tool_choice で、構造化された出力を強制する。
  3. 長い仕様書は、分割して処理する（既定で最大40）。表が読めない場合は、警告に記録する。
  4. 仕様書がない場合は、この工程を飛ばす。項目書の生成は、観点のカタログだけで行う（仕様との照合と、仕様のカバレッジは、仕様書がある場合のみ）。

4.3 下見（recon_site）

Playwrightで、トップからリンクをたどり、SiteMap（ページのURL・タイトル・画面の種類）を作る（AIは使わない。最大12ページ）。画面の種類（top／list／detail／form／cart／checkout／static）は、URLの形とフォームの有無で判定する。開発環境のモードでは、商品ページで「カートに入れる」を押して、決済画面まで進み、決済画面を、記録する（状態を変える操作は、テスト環境の宣言・承認がある範囲だけ。クリック数に上限）。読み取り専用のモードでは、robots.txtを確認し、GETだけで、低速に閲覧する。

4.5 承認とポリシーゲート

4.6 実行と判定（loop.py／judging.py）

  1. 承認済みの項目を、順に実行する。1項目あたり最大8ターン。同じ状態が3回続いたら、詰まりとして記録する。
  2. 観察は、画像ではなく、テキストと操作できる要素の一覧。各ステップの直前に、個人情報をマスクする。
  3. AIが、ツール（navigate／click／select_option／scroll／get_page_state／finish_test_case）を選ぶ。能動マクロ（rapid_click／navigate_direct／fill_abnormal／override_param）は、P-SECの項目だけ。
  4. 合否は、judging.py が、コードの根拠で判定する。根拠が弱い場合は、needs_review。
  5. 項目書の後に、探索的テスト（最大30ステップ。最低5ステップは、続ける）。能動マクロは、コードで拒否。
  6. 不具合票を作る（観点・重大度・確度・種類・仕様参照・期待と実際・スクリーンショット・再現手順）。完全一致、または、仕様参照・観点・種類・正規化したタイトルが一致するものは、1件に統合。

4.7 費用の管理

4.8 ジョブキュー（queue/JobQueueService）

状態意味遷移のきっかけ
queued承認済みで、順番待ち承認（POST /plans/{id}/approve）、再実行
runningワーカーへ依頼済み組織の実行中が2件未満になり、先頭からディスパッチ（3秒間隔＋承認直後）
completed／failed／cancelled／interrupted／timeout終了ワーカーへの問い合わせで確定。使用量を1回だけ記録。既定900秒を超えると timeout（打ち切り）

Java再起動時は、DB上で queued／running のままの実行を、ワーカーへ問い合わせて整理する。ワーカーが止まっているときは、例外にせず、「まだ実行中」として、次の同期を待つ。DB上の実行ID（安定）と、ワーカー側の実行IDは、分けて持つ。

4.9 認可の決定（Web層）

プロジェクトの種類URLの分類決まるモード必要な確認
開発環境ローカル・プライベートlocalテスト環境の宣言
開発環境公開ホストstaging所有確認（/.well-known/）＋宣言
公開ページ公開ホストreadonly規約・robots.txtの確認への同意
いずれもメタデータのアドレス・拒否リスト登録できない―

種類は、作成後に変更できない。ワーカーへは、authorization（host・verified・testEnvDeclared・consentId・mode）を、実行のたびに渡す。mode=readonly のとき、ワーカーは、他の判定より前に、読み取り専用の制約（GET以外の遮断、robots.txt、低速、UA、429/503で停止）を、無条件で適用する。

4.10 AI呼び出しの回復（llm.py）

事象対応
429Retry-After を守って待つ（最大20秒）。最大4回
5xx・タイムアウト（30秒）再試行
不正なJSON・ツール引数再試行
無料枠の拒否有料モデルへ、自前で切り替え
主モデルの失敗別ベンダーのモデルへフォールバック（実測: 3/3完走）
guardrail_blocked（400）失敗として記録し、そのステップを諦めて、実行は続ける

4.11 不具合の状態管理

不具合票は、FindingFingerprint（観点・種類・正規化したタイトルなど）で、実行をまたいで同一視される。状態は、未対応／対応済み／対応しない。「対応しない」は、以降の実行の一覧で、抑制される。一覧は、既定で、未対応のみを表示（「すべて」で全件）。

10. 拡張のしかた

やりたいこと触る場所注意
観点を足すagent/perspectives.py（データの辞書）読み取り専用で許可するかは、READONLY_ALLOWED_PERSPECTIVES。危険度の判定も
コードでの判定を足すagent/judging.py に関数を足し、judge() の分岐へ根拠が取れないときは、needs_review に倒す。テストを足す
能動マクロを足すagent/browser.py（ツール定義と実装）、agent/policy.py（上限・許可）P-SEC専用。探索では拒否される。無害な文字列だけを使う
定型の項目を足すagent/planning.py の定型項目の生成読み取り専用では、作らない
モデルを変える.env の ORCA_MODEL、フォールバックの設定コードにIDを書かない。変更後にベンチで確認
画面を足すweb/.../templates/ と Controller組織のスコープ確認、CSRF、監査ログ
テーブルを足すFlywayの新しい版（V11〜）組織IDを持たせ、他組織の取得をテスト
LPの内容を変えるlanding-app/.../StaticContentRepository.java、JSP数字は、実測値のみ。CSPのため、インラインのstyle・scriptは使わない

11. 既知の制約

  • 実行のたびに、AIの進め方がばらつく（非決定的）。検出率には、幅がある（基本 6〜7/8、能動テスト 3〜4/6）。
  • 緊急停止は、協調的（実行中のAI呼び出しが終わるまで反映されない。最短5秒、30秒を超える場合もある）。
  • 使いやすさ・アクセシビリティは、AIによるチェックリスト判定で、コードでの根拠づけが、限定的。
  • 個人情報のマスクは、正規表現で、不完全。上流のAI事業者でのデータの扱いは、確認中。
  • OrcaRouterのFirewall評価APIは、未接続（自前のポリシーゲートで代替）。ガードレールは、合成して、キーに紐付けたが、動作の確認は、これから。
  • Web層のDBは、H2（ファイル）。複数台での運用や、保存時の暗号化は、未対応。
  • ジョブ単位のリトライ、公平なスケジューリング、管理者画面は、範囲外。
  • スキャン画像のPDF（OCR）は、非対応。
